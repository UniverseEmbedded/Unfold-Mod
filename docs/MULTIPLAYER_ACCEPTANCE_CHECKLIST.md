# 联机验收清单（规格 §6 必须联机项）

对应 `docs/SPEC-UNFOLD-ALGORITHM.md` §6 第 5、6、8、9 条。适用：Minecraft 1.21.5 + Fabric Loader + Fabric API + 本 mod，**客户端与服务端安装同一提交**。

本文只写验收步骤，不代表已经执行过。每节按「目标 / 前置 / 搭建 / 步骤 / 观测 / 判据 / 失败处置」填写，结论要么「通过」，要么「失败」，构造不出来就写「构造不稳定」，不要写「看起来正常」。

## 0. 通用前置

- 安装：同一个 mod jar 分别放进服务端 `mods/` 与客户端 `mods/`；服务端与客户端的 Fabric Loader、Minecraft 1.21.5、Fabric API 版本一致；用 `fabric-server-launch.jar` 启动。
- `server.properties` 设 `online-mode=false`，`server-port` 任选；客户端用「直接连接」进 `localhost:<port>`。
- 创造模式，`logs/latest.log` 可读。
- 一个客户端即可；只有第 2 节建议两个客户端（或第二人用服务端控制台）。
- 需要的日志：服务端 `logs/latest.log`（本 mod 的 `rejected`、`Teleported to` 与 Vanilla 的 `moved too quickly` / `moved wrongly`）；客户端 `.minecraft/logs/latest.log`（`Teleported to`）。
- 世界中所有坐标以锚点 `(0,100,0)` 为例。若该处已有方块，换一块空域或整体平移，不要边搭边拆原地图。
- 每次测试前先退出再进入展开模式（按 `V` 两次），清空 `pendingTeleportTarget`、`lastHorizontalCutBlock`、`jumpLayerDirection` 等跨会话状态。
- **按空格触发切层时不要同时按 WASD。** A4 门控在玩家已有输入位移时会判定「原版已经完成期望的屏幕位移」并直接跳过展开逻辑，按着移动键测不出切层。
- 记录模板：

```
提交哈希：
客户端 tick 率（F3 左上）：
触发前坐标：
触发后 1 tick 坐标：
触发后 1 秒坐标：
服务端日志命中原行：
客户端日志命中原行：
结论（通过 / 失败 / 构造不稳定）：
备注：
```

## 1. 服务端拉回阈值（`moved too quickly` / `moved wrongly`）

### 目标

确认大位移切层不会被服务端当成作弊拉回；即使出现 `moved too quickly` / `moved wrongly` 日志，客户端最终也能收敛到服务端权威位置，不出现来回跳。

### 前置

- 1 个客户端，创造模式。
- 服务端 INFO 日志即可，不需要 debug。
- 服务端 TPS 正常（`/debug` 或 F3 服务端 tick 时间稳定），否则网络延迟会把拉回与超时混在一起。

### 搭建

RIG-A：垂直模式 36 格切层样本。顶面 `y=101` 与 `y=137`。

```
fill -2 100 -2 2 100 2 minecraft:stone
fill -2 136 -2 2 136 2 minecraft:stone
```

RIG-B：斜向模式接近上界的样本，位移约 110.85 格（`λ = Δy / 0.57735 = 64 / 0.57735`）。

```
fill -2 100 -2 2 100 2 minecraft:stone
fill -1 164 -1 1 164 1 minecraft:stone
fill -66 164 62 -60 164 67 minecraft:stone
```

### 步骤

1. 客户端站到 RIG-A 底层中心 `(0.5, 101, 0.5)`。
2. 视角 `yaw` 任意、`pitch = -90°`（垂直向上看），按 `V`，确认聊天栏显示「垂直模式」。
3. 松开所有移动键，只按一次空格；触发后立刻记录 F3 坐标。
4. 保持不动 1 秒，再记录一次坐标。
5. 换 RIG-B：`yaw = 45°`、`pitch = -35.26°`（`ISO_POS_X_POS_Y`），按 `V` 进入斜角模式；同样松开移动键只按空格，记录前后坐标。
6. 服务端日志与客户端日志各保留一段覆盖整个过程的片段。

### 观测

- 客户端日志：`Teleported to {x,y,z} (client prediction, awaiting server authority)`，核对打印的坐标是否为目标。
- 服务端日志：`teleport rejected`、`moved too quickly`、`moved wrongly`，记原文与时间戳。
- F3 坐标：触发前、触发后 1 tick、触发后 1 秒三组。
- 期望目标：RIG-A `(0.5, 137, 0.5)`；RIG-B 约 `(-63.5, 165, 64.5)`（±0.3 内即可）。

### 判据

- **通过**：1 秒内客户端坐标稳定在期望目标 ±0.5，且没有回到 `(0.5, 101, 0.5)`；服务端日志没有 `teleport rejected`。
- **通过（容忍）**：出现 `moved too quickly` / `moved wrongly`，但最终权威位置仍是目标，且只纠正一次。
- **失败**：客户端被拉回原位；或服务端对合法目标返回 `rejected`；或在目标与原位之间反复跳动；或 RIG-B 的位移被 `DISTANCE_EXCEEDED` 拒绝。

### 失败处置

1. 退出展开模式（`V`），站回底层。
2. 保留服务端与客户端日志片段、三组坐标、视角角度、客户端 tick 率。
3. 不改 `MAX_REQUEST_DISTANCE`，不调 `vanillaMeetsDesiredMotion` 阈值；把失败写进记录，附位移与方向。
4. 若失败只出现在 RIG-B（约 111 格），在备注里注明「上界样本」，与普通位移样本分开处理。

## 2. NO_SUPPORT 保持位置

### 目标

确认服务端返回 `NO_SUPPORT` 时，客户端**不在同一 tick 内**把位置回退到预测前的位置；预测位置保持到服务端权威纠正到达为止，且不产生反复切层。

### 前置

- 2 个客户端（A 触发、B 拆支撑），或 1 个客户端 + 服务端控制台。
- 客户端 A 需要能录屏（60 fps），因为「是否在同一 tick 回退」只能靠画面帧判断，日志里没有客户端回执记录。
- 建议关掉客户端区块动画/平滑摄像机，减少目测误差。

### 搭建

RIG-N：1×1 支撑，方便整块移除。顶面 `y=101` 与 `y=137`。

```
fill -2 100 -2 2 100 2 minecraft:stone
setblock 0 136 0 minecraft:stone
```

### 步骤

1. A 站底层 `(0.5, 101, 0.5)`，`pitch = -90°`，按 `V` 进入垂直模式，松开移动键。
2. B/控制台在 A 按空格前约 1 秒执行 `setblock 0 136 0 air`，A 按空格；若 A 未触发（候选池为空），B 恢复 `setblock 0 136 0 stone` 并重试。
3. 重复最多 20 次，直到服务端日志出现一条 `teleport rejected: NO_SUPPORT at (0.5, 137.0, 0.5)`。
4. 对每一次成功采到的样本，保留录屏中「按空格前 → 回执后 5 tick」的片段。

### 观测

- 服务端：`teleport rejected: NO_SUPPORT at ...`（原文与时间戳）。
- 客户端 F3 坐标逐帧：应出现「137 停留至少 1 tick」再变化；不得出现「回执当帧直接 101」。
- 客户端日志：`Teleported to` 只出现一次；若连续出现，说明 pending 没被清。

### 判据

- **通过**：客户端在预测位置至少保持 1 tick，随后由服务端权威位置或重力收敛；`Teleported to` 不连续出现。
- **失败**：回执当帧位置直接跳回预测前位置（说明走的是 `DISTANCE_EXCEEDED`/`COLLISION` 回退分支，不是 `NO_SUPPORT` 保持）；或位置在 101/137 之间反复。
- **构造不稳定**：20 次内没有采到 `NO_SUPPORT`。写「构造不稳定」，不记失败，但记录尝试次数与每次时序。

### 失败处置

1. 退出展开模式，A 站回底层。
2. 保留服务端日志、录屏、20 次时序记录。
3. 不修改 `TeleportTargetValidator` 或 `handleTeleportResponse`；把「是否为竞态构造失败」先在备注里判清，再决定是否另开任务。

## 3. 抑制 / 前瞻参数（2.5 格与 0.2 格）

### 目标

分别确认：同层反向往返被 2.5 格半径抑制；候选处的横向前瞻 0.2 格能阻止「切层后仍被同一面墙挡住」的假切层。层滞回只约束同一次跳跃，落地即清。

### 前置

- 1 个客户端，创造模式。
- 需要读客户端 `Teleported to` 的出现次数与坐标；不需要服务端日志（这些参数全在客户端）。

### 搭建

RIG-H：走廊 + 深度墙。走廊两侧墙保证玩家持续处于「即将水平碰撞」，深度墙提供可穿越的层。

```
fill -20 100 -3 4 100 8 minecraft:stone
fill -20 100 -3 4 103 -3 minecraft:stone
fill -20 100 8 4 103 8 minecraft:stone
fill -8 100 -3 -8 103 8 minecraft:stone
```

`d` 为 `POS_X`：`(-1,0,0)`。水平模式下移动方向是 `d×Y = (0,0,-1)`，即按 `D`（右）向 `-Z` 走。

### 步骤

1. 站到 `(2.5, 101, 2.5)`，`yaw = 90°`、`pitch = 0°`，按 `V`，聊天栏应显示「水平模式」。
2. 按住 `D` 约 1 秒，直到撞上 `z=-3` 的走廊墙。预期发生一次切层，落点约 `(-8.31, 101, 2.5)`（`x` 减少约 10.8，`y`、`z` 不变）。
3. 保持 `D` 按住 2 秒，观察是否出现第二次 `Teleported to`；按设计应没有（2.5 格抑制）。
4. 松开 `D`，按 `A` 向 `+Z` 走约 3 格离开深度墙，再走回来重新撞墙；预期恢复允许切层（抑制只覆盖 2.5 格内的相邻往返）。
5. 0.2 格前瞻：先在候选落点沿移动方向 `-Z` 的半格范围内放一格障碍（按 F3 当时的 `z` 读数取坐标，例如 `setblock -9 101 -2 minecraft:stone`），重复步骤 2，预期**不**切层；`setblock -9 101 -2 minecraft:air` 后重复，预期切层。
6. 层滞回：在垂直模式（RIG-A）跳到上层后，未落地前尝试再按空格或潜行下落，预期同一次跳跃内不允许反向换层；落地后再操作，允许。

### 观测

- 客户端 `Teleported to` 的次数、时间戳、坐标。
- 步骤 2 落点的 `y` 必须与站立面一致（水平模式 `d⊥Y`，不应改变世界 `Y`）。
- 步骤 3 的 2 秒内是否出现第二次切层。
- 步骤 5 有/无障碍时的切层结果对照。

### 判据

- **通过**：步骤 2 恰好一次，位移只沿 `x`；步骤 3 无第二次；步骤 4 走远后可再次切层；步骤 5 有障碍不切、无障碍切；步骤 6 落地前不反向换层。
- **失败**：步骤 3 每 1–2 tick 出现一次切层；或步骤 2 的 `y` 改变；或步骤 5 两态结果相同（0.2 前瞻没生效）。
- **需确认**：步骤 4 需要多次尝试才能恢复切层，记录「离开距离」与「恢复所需 tick 数」。

### 失败处置

1. 退出展开模式，站回走廊起点。
2. 保留客户端日志与每次坐标。
3. 不改 `REVERSE_CUT_RADIUS`、`LATERAL_LOOKAHEAD`；若 0.2 前瞻失败，先确认障碍块确实在候选点的碰撞箱内（按 F3 坐标复核），再记失败。

## 4. 超时窗口（20 tick）

### 目标

确认 `pendingTeleportTarget` 在无回执约 20 tick 后被丢弃，冻结期间不重发，解冻后请求最多结算一次，且之后还能再次切层。

### 前置

- 1 个客户端 + 专用服务端；服务端控制台有 OP 权限。
- 服务端支持 `/tick freeze` / `/tick unfreeze`（1.20.4 及以上）。
- RIG-A（第 1 节）即可。

### 步骤

1. 客户端站在 RIG-A 底层，`pitch=-90°`，按 `V`，松开移动键。
2. 按空格触发切层；在同一 tick 内由控制台执行 `tick freeze`。
3. 冻结保持 2 秒（约 40 客户端 tick，超过 20 tick 的超时窗口）。
4. 执行 `tick unfreeze`。
5. 解冻后 5 秒内观察位置；再走开、重新站回、按空格一次，确认还能切层。

### 观测

- 冻结期间客户端 `Teleported to` 是否只出现一次（客户端 tick 继续运行，超时判定在客户端）。
- 冻结期间 F3 坐标是否稳定在目标（不因服务端冻结而抖动）。
- 解冻后服务端日志是否出现新的一次结算（`teleport rejected` 或权威位置包导致的纠正）。
- 解冻后 5 秒内位置是否稳定在目标或回到原位（二者取其一，不反复）。
- 再次按空格是否产生新的 `Teleported to`（证明 pending 已清、冷却已复位）。

### 判据

- **通过**：冻结期间无第二次请求；解冻后只结算一次；位置最终稳定；再次切层可用。
- **失败**：冻结期间每 2 tick 重发（`Teleported to` 连续出现）；解冻后位置在两值间反复；或解冻后永久无法再触发切层。
- **需确认**：解冻后既没有接受也没有拒绝，位置长期停在预测点（记录服务端是否仍在处理旧请求）。

### 失败处置

1. 退出展开模式，站回底层。
2. 保留两端日志、冻结时长、解冻前后的坐标。
3. 不改 `PENDING_TELEPORT_TIMEOUT_TICKS`、`TELEPORT_REQUEST_INTERVAL_TICKS`；把「冻结时长 / 解冻时刻」写进记录，便于区分客户端超时与服务端排队。
